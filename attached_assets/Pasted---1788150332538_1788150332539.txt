Добавь защиту от повторной обработки одного и того же комментария и от двойного автоматического ответа.

Цель:
Гарантировать, что Telegram-комментарий не будет повторно обработан и бот не отправит два одинаковых ответа при:
- повторной доставке Telegram update;
- задержке очереди;
- перезапуске workflow;
- повторном попадании одного события в очередь;
- ошибке после анализа AI.

Важно:
Не ломай текущую архитектуру.
Не изменяй OpenRouter, модель, max_tokens=8192, Secrets, workflow и healthcheck без необходимости.

Текущая логика коротких комментариев должна остаться без изменений:
- простые реакции и благодарности не отправляются в AI;
- короткие комментарии с вопросом отправляются в AI;
- очередь комментариев продолжает работать.

Нужно реализовать идемпотентную обработку комментариев.

1. Используй уникальный идентификатор комментария.

Найди существующие поля модели/таблицы комментариев и используй стабильный идентификатор Telegram-сообщения вместе с идентификатором чата/канала, если это необходимо для уникальности.

Например логически:

(chat_id, message_id)

или существующий уникальный comment/message identifier.

2. Перед постановкой комментария в обработку или перед его фактической обработкой проверять:

- не был ли комментарий уже полностью обработан;
- не находится ли он уже в процессе обработки;
- не был ли на него уже опубликован автоматический ответ.

Если комментарий уже обработан:
- не отправлять его повторно в AI;
- не создавать повторный ответ;
- записать понятный лог;
- безопасно завершить обработку.

3. Добавь защиту от гонки.

Важно:
если два worker одновременно получили один и тот же комментарий, оба не должны пройти проверку и создать два ответа.

Используй подходящий для текущей SQLAlchemy/SQLite архитектуры атомарный механизм:
- уникальное ограничение;
- атомарную вставку/захват обработки;
- или другой безопасный механизм, совместимый с текущей базой.

Не делай защиту только через Python set в памяти, потому что после перезапуска workflow он очистится.

4. Добавь понятные статусы обработки.

Если текущая модель позволяет, используй или добавь минимально необходимые статусы, например:

pending
processing
processed
replied
failed

Но не усложняй схему без необходимости.

Главное правило:

один Telegram-комментарий -> максимум один AI-анализ -> максимум один опубликованный автоматический ответ.

5. Поведение при ошибке AI.

Если AI-запрос завершился ошибкой:
- не публиковать пустой ответ;
- не считать комментарий успешно отвеченным;
- сохранить информацию об ошибке согласно текущей архитектуре;
- не допустить повторной автоматической публикации уже созданного ответа.

Не меняй существующую обработку ошибок без необходимости.

6. Поведение после успешного ответа.

После успешной публикации автоматического ответа:
- зафиксировать, что ответ уже опубликован;
- сохранить идентификатор ответа, если текущая архитектура это поддерживает;
- повторный запуск того же комментария не должен создавать новый ответ.

7. Добавь подробные логи.

Нужны сообщения примерно такого смысла:

Comment skipped: already processed
Comment skipped: already processing
Duplicate comment prevented
AI analysis completed
Auto reply published
Auto reply skipped: already published

В логах должен быть идентификатор комментария.

8. Добавь тесты.

Минимум проверить:

A. Один комментарий дважды передаётся в обработку:
ожидается один AI-анализ и максимум один ответ.

B. Один комментарий дважды попадает в очередь:
ожидается одна фактическая обработка.

C. После успешного ответа повторная обработка:
AI повторно не вызывается и новый ответ не публикуется.

D. Простая реакция:
повторная обработка не вызывает AI и не создаёт ответ.

E. Ошибка AI:
пустой ответ не публикуется.

F. Два параллельных вызова обработки одного комментария:
должен обработаться только один экземпляр.

9. Сначала изучи существующие:
- модели database;
- repositories;
- comment processing handler;
- queue;
- текущие тесты.

Используй существующую архитектуру и меняй минимальное количество файлов.

10. После изменений обязательно выполнить:

python -m compileall -q app tests
python -m pytest -q

11. Если тесты проходят:
перезапусти только workflow:

Start application

После запуска проверь:

- Start application running;
- Telegram polling стартовал;
- Comment processing queue started;
- GET http://127.0.0.1:8080/health возвращает HTTP 200.

12. В конце покажи отчёт:

- какие файлы изменены;
- как реализована защита от дублей;
- какой уникальный идентификатор используется;
- как предотвращается race condition;
- результаты всех тестов;
- healthcheck;
- подтверждение, что один комментарий не может получить два автоматических ответа.

Остановись на первой новой технической ошибке и не вноси дополнительные несвязанные изменения.
